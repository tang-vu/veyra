# VEP-0001: Transaction and effect protocol v1

- Status: Accepted
- Version identifier: `veyra.protocol/v1`
- Authors: Veyra contributors
- Date: 2026-08-23

## Abstract

This VEP defines the first Veyra wire protocol: principals express intents, planners propose typed
effects, policy binds capabilities and approvals to canonical content, the kernel records execution
and verification, and adapters report honest recovery semantics.

The generated JSON Schemas in `packages/protocol-schema/schema/` are authoritative for serialized
shape. The Rust types in `veyra-protocol` are authoritative for semantics where this text is
ambiguous.

## Conventions

- JSON object keys not declared by a type are rejected for security-sensitive records.
- Identifiers are strongly typed UUIDs serialized as hyphenated strings.
- Timestamps are UTC RFC 3339 values.
- Serialized enum variants use `snake_case`.
- Every versioned object carries `schema_version: "veyra.protocol/v1"`.
- Digests are lowercase SHA-256 hex over RFC 8785/JCS canonical JSON.
- `Effect.inputs` values are either `{ "kind": "public", "value": … }` or a secret reference.
  Raw secret material is never a valid secret-reference encoding.

## Records

`Principal` identifies a human, agent, or service. `Intent` names its principal, human-readable
summary, requested resource envelopes, secret-safe context, and creation time. An intent does not
carry authority.

`Plan` contains ordered `Step` values; a step contains ordered `Effect` values. Each effect declares:

- stable ID and causal `(intent, plan, step, optional effect)` parent;
- principal, adapter, operation, typed inputs, and exact resource;
- reserved preconditions and expected postconditions;
- risk and `reversible | compensatable | irreversible` classification;
- preview, idempotency key, timeout, retry policy, capability requirements, and optional inverse.

Supported resource variants describe filesystem paths or sets, HTTP origin/path, process
executable/workdir, and adapter-defined namespaces. An adapter must reject a resource variant it does
not understand. A plan is invalid when any effect is outside every `Intent.requested_resources`
envelope. Bundled adapters accept an exact operation-specific set of input names and reject unknown
or ignored fields. V0.1 rejects every non-empty `preconditions` list because the protocol does not
yet define an adapter evaluation interface for them; it never treats an unevaluated condition as
satisfied. Expected postconditions must be non-empty, unique, well formed, supported by the selected
adapter, and observable within the effect's declared scope.

`Capability` binds authority to a principal and optionally an intent and transaction. It also binds
adapter, operations, resource envelopes, constraints, validity window, nonce, maximum uses, and issue
time. Absence of a matching live capability is denial.

`PolicyDecision` records outcome, reasons, contributing capabilities, and the preflighted effect
digest. `ApprovalRequest` adds exact risk, resource, preview, nonce, and expiry. `ApprovalGrant`
repeats transaction, request nonce, digest, approver, and expiry. A request nonce is consumable once.

`Execution` identifies one attempt. `Receipt` binds execution, transaction, effect, effect digest,
outcome, result digest, redacted result, issue time, key ID, and local authentication tag.
`Verification` contains every postcondition check. `Compensation` records whether restoration was
verified and preserves safe details. None of these records retrospectively grants authority.

`AuditEvent` has a monotonically increasing sequence, optional transaction, event type, causal
parent, redacted payload, previous hash, own hash, and record time. The chain starts with an empty
previous-hash slot represented by 64 lowercase zeroes. It is tamper evidence under the local trust
assumptions, not a consensus ledger. Audit payloads bind the latest transaction snapshot, immutable
objects, capability facts, approval replay rows, staged descriptors, and idempotency rows to the
chain; full verification checks both the event chain and those materialized views.

## State machine

The normal path is:

```text
draft → planned → preflighted → awaiting_approval → approved → staged
      → executing → verifying → committed
```

Preflight may auto-approve when policy requires no human action, or end in `denied`. Explicit edges
also lead to `cancelled` and `failed`. Recovery uses `compensating`, `rolled_back`,
`partially_compensated`, and `manual_recovery`. Terminal states have no general restart edge. A
transaction snapshot has a monotonically increasing `revision`; stale writers must fail.

## Authorization and approval

Policy evaluation is conjunctive. A capability matches only when its principal, bindings, adapter,
operation, resource, requested constraints, validity window, nonce/status, and remaining uses cover
the effect. Resource comparison is structured—never a substring or glob comparison.
The kernel enforces the global `max_timeout_ms`, `max_risk`, and `allow_irreversible` caveats.
Adapter-specific caveats must be repeated exactly by the effect and rejected by adapter validation
unless that adapter implements their semantics; bundled adapters reject all unknown caveats.

The kernel first evaluates proposal-level authority before permitting adapter observation. A denied
effect records a redacted denial without invoking preflight. For authorized proposals, preflight
must complete before approval so the exact preview is included in the digest, and policy is then
reevaluated over that preflighted content. At execution the kernel recomputes the effect digest and
requires it to equal both the policy decision and approval grant. Capability uses and an optional
approval nonce commit atomically with audit evidence for each effect; the idempotency reservation is
also durable before the adapter crosses the side-effect boundary. During multi-effect authorization,
the kernel virtually reserves uses so one capability cannot be knowingly overbooked by the plan.

An `approver_id` is an audit identity, not by itself proof of a human-authentication ceremony. The
V0.1 local API authenticates one administrative controller bearer and trusts that controller to
nominate the registered human. Deployments must not expose that bearer to a planner.

## Execution and recovery

Adapters implement `validate`, `preflight`, `stage`, `execute`, `verify`, and `rollback`. Preflight is
non-mutating. Stage may persist restoration material but must not apply the declared external effect.
Execute receives the staged descriptor bound to both effect ID and digest. Results and recovery
details must be bounded and secret-safe. A process preview additionally binds the SHA-256 digest of
the executable bytes; stage and execution recheck that digest. The final check-to-OS-spawn interval
cannot be made atomic on every supported platform and remains a documented host-level race.

`reversible` means restoration can be verified within the adapter's contract and preconditions.
`compensatable` means a distinct best-effort effect can reduce impact but may not recreate the prior
state. `irreversible` means Veyra offers no rollback claim. Arbitrary shell commands cannot be
declared reversible. The HTTP adapter accepts `reversible` only for `GET`, `HEAD`, and `OPTIONS`;
operators are responsible for allowlisting services that honor those methods' no-mutation semantics.

An idempotency key is 1-256 restricted ASCII characters and must be unique per adapter within a
plan. It has one durable outcome. A second caller receives the prior result or a conflict; it does
not invoke the adapter twice. If a crash occurs after the side-effect boundary but before an outcome
is durable, status is unknown and human recovery is required. Rollback recovers every available
durable stage in reverse order; missing stage evidence forces `partially_compensated` rather than a
false claim of complete restoration.

Although `RetryPolicy` is present for forward compatibility, V0.1 accepts only
`max_attempts: 1`, `backoff_ms: 0`, and an empty `retryable_errors` list. The kernel never
automatically retries an adapter; idempotency protects repeated explicit requests.

## Compatibility

Additive documentation and new optional client behavior do not change the protocol version. Adding
required fields, changing canonicalization, changing enum meaning, or changing authorization
semantics requires a new protocol identifier and migration plan. Schemas are regenerated from Rust
and checked byte-for-byte in CI. Readers must reject unsupported `schema_version` values rather than
silently reinterpret them.

## Security considerations

The protocol assumes a trusted kernel, journal implementation, configured adapters, local key files,
and host OS. It treats planners, model output, intent text, clients, external HTTP data, process
output, and workspace contents as untrusted. See the threat model for attacks and residual risk.
